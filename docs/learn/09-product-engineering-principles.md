# 09. 프로덕트 엔지니어링과 기획 원칙

**한 줄 요약** — 좋은 제품은 "무엇을 만들까"보다 "누구의 어떤 경험을 위해, 왜 만들까"에서 시작한다.

## 쉬운 비유
밭에 아무 씨앗이나 뿌리지 않아요. 계절, 흙, 먹을 사람을 생각하고 무엇을 심을지 정하죠. 제품도 **사용자와 목적을 먼저 정하고** 기능을 고릅니다.

## 핵심 개념
- **핵심 경험** — 이 제품이 꼭 지켜야 할 한 가지 느낌. 이 게임에서는 *"편안함"*
- **문서 우선** — 코드보다 문서로 방향을 먼저 맞추면, 잘못된 방향으로 많이 만드는 낭비를 줄임
- **완료 기준** — "언제 다 됐다고 할지"를 미리 정하기 (→ `docs/PLAN.md` 단계별 ✅)
- **작게 만들고 자주 확인** — 큰 기능을 한 번에 만들기보다 작은 단계로 나눠 확인
- **트레이드오프** — 모든 걸 다 가질 수는 없음. 무엇을 포기했는지 기록하기

## 게임 속에서는: 기획이 기술 결정을 만든 예
| 기획 원칙 | 기술 결정 |
|---|---|
| 힐링 — 쉬어도 손해 보지 않기 | 오프라인 동안 친구들이 물주기·수확, 작물이 시들지 않음 |
| 공정함 — 규칙을 어기면 확실한 결과 | 변조 시 메뚜기 떼 + 완전 초기화, 단 파일 손상은 복구로 구분해 억울한 초기화 방지 |
| 직접 돌보는 재미 유지 | 자동화에 연료 제한 |
| 누구나 고칠 수 있게 | 빌드 도구 없음, 데이터는 JSON, 그림은 1장 1파일 |
| 정직한 학습 | 게임 속 보안의 한계를 문서에 명시 |

## 실제 제품에서는
회사에서도 기획서 → 설계 문서 → 개발 → 확인 순서로 일해요. 특히 **"왜 이렇게 만들었는지"를 남기는 문서**는 나중에 합류한 동료에게 큰 선물이 됩니다.

## 직접 해 보기
1. `docs/PLAN.md`의 "확정된 기획 결정" 하나를 골라, 나라면 다르게 정했을지 그 이유와 함께 적어 보기
2. 새 기능 아이디어를 "누구를 위해 / 왜 / 완료 기준" 세 줄로 적어 보기
