# 09. 프로덕트 엔지니어링과 기획 원칙

**한 줄 요약** — 좋은 제품은 "무엇을 만들까"보다 "누구의 어떤 경험을 위해, 왜 만들까"에서 시작한다.

## 쉬운 비유
밭에 아무 씨앗이나 뿌리지 않아요. 계절, 흙, 먹을 사람을 생각하고 무엇을 심을지 정하죠. 제품도 **사용자와 목적을 먼저 정하고** 기능을 고릅니다.

## 핵심 개념
- **핵심 경험** — 이 제품이 꼭 지켜야 할 한 가지 느낌. 이 게임에서는 *"편안함"*
- **문서 우선** — 코드보다 문서로 방향을 먼저 맞추면, 잘못된 방향으로 많이 만드는 낭비를 줄임
- **완료 기준** — "언제 다 됐다고 할지"를 미리 정하기 (→ `docs/PLAN.md` 단계별 ✅)
- **작게 만들고 자주 확인** — 큰 기능을 한 번에 만들기보다 작은 단계로 나눠 확인
- **피드백 반영** — 써 본 사람의 말을 듣고 방향을 고치기. 처음 계획이 틀릴 수 있다고 인정하기
- **하위 호환** — 새 버전이 나와도 전부터 쓰던 사람의 데이터와 습관을 지켜 주기
- **트레이드오프** — 모든 걸 다 가질 수는 없음. 무엇을 포기했는지 기록하기

## 게임 속에서는: 기획이 기술 결정을 만든 예
| 기획 원칙 | 기술 결정 |
|---|---|
| 힐링 — 쉬어도 손해 보지 않기 | 오프라인 동안 친구들이 물주기·수확 (`web/time/helpers.js`) |
| 힐링 — 나쁜 일은 일어나지 않기 | 날씨는 돕기만 함 (비는 작물이 좋아하는 촉촉함으로). 스마트팜이 실패해도 작물은 무사 |
| 공정함 — 규칙을 어기면 확실한 결과 | 변조 시 완전 초기화. 단 파일 손상은 복구로 구분해 억울한 초기화 방지 |
| 직접 돌보는 재미 유지 | 자동화에 연료 제한 (🚧 8단계) |
| 누구나 고칠 수 있게 | 빌드 도구 없음, 데이터는 JSON, 그림은 1장 1파일 |
| 정직한 학습 | 게임 속 보안의 한계를 문서에 명시 (07번 위협 모델) |

## 이 프로젝트에서 실제로 있었던 일
| 무슨 일 | 어떻게 했나 | 배운 점 |
|---|---|---|
| "시드는 건 넣지 말지 그랬니. 힐링 게임이라니깐" | 시듦 기능을 빼고, 옛 세이브의 시든 작물은 수확할 수 있게 되살리는 마이그레이션(버전 3) | 기능이 핵심 경험과 어긋나면 만든 것도 뺀다 |
| 작물을 4가지 → 14가지로 늘림 | 전부터 키우던 농장에는 "새 씨앗 선물"을 **한 번만** 보냄 (`meta.knownSpecies`, `web/farm/seed-gift.js`) | 새 기능이 기존 사용자를 소외시키지 않게 |
| "스크롤 내리는 상황을 최대한 줄이게" | 메뉴 접기·팝업·새 창, 씨앗은 그림 칸, 부엌은 만들 수 있는 요리 먼저 | 사용자가 불편을 말해 주면 화면 구조를 다시 생각 |
| Windows 에서 서버 창에 오류 메시지가 뜸 | 오류를 그대로 재현하는 테스트를 먼저 만들고(`test_client_leaving_early_does_not_print_traceback`), 고친 뒤 통과 확인 | 버그는 "재현 → 고치기 → 다시 안 생기게 테스트" |
| 휴대폰으로도 하고 싶다 | 서버를 와이파이에 여는 보안 결정이라 보류하고 이유를 기록 | 편리함 vs 안전함, 결정은 사용자와 함께 |

## 실제 제품에서는
회사에서도 기획서 → 설계 문서 → 개발 → 확인 순서로 일해요. 특히 **"왜 이렇게 만들었는지"를 남기는 문서**는 나중에 합류한 동료에게 큰 선물이 됩니다. Git 커밋 메시지도 그런 기록이에요.
